## 它是什么

一个只干一件事的小命令行工具：把「源仓库里的规则文件和技能目录」同步到「编辑器真正去读的运行时目录」。

它同步两处（都写在 `sync.config.json` 里）：

| 源（你编辑这里） | 目标（编辑器读这里） | 做成什么 |
|---|---|---|
| `D:\Seed\my-rules\rules\` | `~\.trae-cn\user_rules\` | 每个 `.md` 一个符号链接，名字加 `rule-` 前缀 |
| `D:\Seed\retro-skills\skills\` | `~\.trae-cn\skills\` | 每个技能目录一个 junction |

**为什么非要这么绕一道**：运行时目录里的东西不在任何 git 里。你要是直接在那儿改，改动会生效，但它没有版本、换机器就丢，而且下一次同步一到就被冲掉 —— 等于白改。所以定了一条规矩：**只改源，然后跑同步**；运行时目录永远只是源的一面镜子。

**为什么用链接而不是复制**：链接是一块指路牌，内容始终读的是源。所以改完源不用重跑同步，下次对话里就是新的。复制则每次都要重来一遍，还容易忘了跑。

## 为什么把它拆成独立项目

### 事情的经过

原来它住在 `retro-skills\scripts\` 里。怎么来的？做复盘套件的"最后一公里安装"时顺手写的，身份是那份套件的一个零件。

后来发现它管的东西**不止 retro-skills**：它同时管 `my-rules` 的规则和 `retro-skills` 的技能。也就是说，它早就不属于某一个仓库，而是这两个仓库之间的一条**公共管道**。

### 当时的争论

- **提出拆分的一方（用户）**："换编辑器是很基础的需求。"
- **反对的一方（AI）**："它现在没坏，也没人抱怨。按我们自己的规矩 —— 一个改动要等到出现真实信号才做 —— 这里没看到信号，先别动。"

用户拍板：**换编辑器就是信号，而且它属于基础需求**。理由两层：

1. 换一次编辑器，要变的东西有三样 —— 源的目录、目标的目录、文件的命名规则。这三样当时**硬编码在脚本里**。不拆开、不改成配置驱动，每次换编辑器都得改代码。
2. 它已经被两个仓库共用了。一条管道该住在自己的房子里，而不是寄居在其中一个客户家里。

**结论：拆成独立项目 + 改成配置驱动。**

这条决定也顺带修正了当初那个"没信号就不做"的判断标准：**信号不该只看有没有人抱怨，还要看这是不是迟早要发生的基础需求**。

### 拆完得到了什么

- **换编辑器 = 改配置**，不碰代码：源、目标、命名规则全在 `sync.config.json`。
- **谁都能用**：别人 clone 下来，把自己的路径填进配置就能跑。
- **职责清楚**：它是"资产同步器"，不再是"复盘套件的一个零件"。

## 为什么名字必须是中性的

因为它**同时管规则和技能**。

如果叫 `my-rules-cli`，名字只说了它管规则，但它还管着 5 个技能。这就像一个人兼着"管仓库"和"管门禁"两份差事，名片上却只印了"仓库管理员"—— 新来的人拿着这张名片找，永远找不到管门禁的那个人。

`agent-assets-sync` 说的是"**智能体资产的同步器**"：规则、技能，以及以后可能有的别的（提示词、模板……）都算智能体的资产，谁来都装得下。名字不绑死在某一个源仓库上。

## 为什么先不发布到 npm

**因为现在没有外人要用它。**

发 npm 是为了"让陌生人一条命令就装上"。但眼下只有本机这一个使用场景，装它的方式无非 `git clone` 下来跑。为了一个还不存在的用户群去搭发布流水线（版本号、打包、发布账号、CI），是**为想象中的需求付真实的成本**。

那什么时候发？看信号，记在 `retro-skills\docs\architecture.md` 的 backlog 里：

- **R31** —— 决定把规则仓库公开分享时，还要额外生成一份对外的兼容产物。
- **R35** —— 同步脚本独立成项目这件事本身；触发信号是"出现第二个使用者 / 决定对外发布 / 要管第 3 个源仓库"。

真到那天再发，不迟。

## 当初怎么搬的（迁移五步）

顺序不能反 —— **必须先在新家跑通、确认运行时一个字没变，才允许把旧家那一份删掉**。

1. **写新家的文件**：`sync.config.json`（把原先硬编码在脚本里的两条目标搬进来）+ `src/sync.mjs`（改成"读配置"）+ 测试 + 本文档。
2. **跑测试**：`node --test test/sync.test.mjs` —— 原有的 14 个用例必须全绿，另外补上 CLI 参数解析与配置解析的新用例。
3. **在新家跑真实同步**：`node src/sync.mjs` —— 必须打印 **"全部一致"**（规则"已就位 9"、技能"已就位 5"）。这一条是**铁证**：说明新脚本对运行时的判断和旧脚本完全一样，运行时一个字都没变。
4. **删旧家的脚本**：删掉 `retro-skills\scripts\`，并把所有指路的文档改到新路径（架构文档、`my-rules\README.md`、相关规则正文）。
5. **用户提交**：各仓库各自 commit（脚本作者不替用户提交）。

## 验收标准（怎么算搬成功）

| # | 标准 | 取数命令 | 搬迁当日结果 |
|---|---|---|---|
| 1 | 测试全绿 | `node --test test/sync.test.mjs` | 26/26 通过 |
| 2 | 新项目跑出"全部一致"，数字与搬家前一致 | `node src/sync.mjs` | 规则"已就位 9"、技能"已就位 5"，**全部一致** |
| 3 | 运行时目录一个字没变 | 上一条的"需建链接 / 需替换 / 待迁移旧名 / 自家残留"四栏**全为 0** | 四栏全 0 |
| 4 | 旧路径已删、没有文档还指向它 | 全文搜 `retro-skills\scripts` | 已删、已无残留指向 |

> 数字只在**本表这一处**留号码，并附上取数命令 —— 写在多处必然漂移。

## 文件地图（CLI 化后的现状；"零第三方依赖"已按用户拍板放开——依赖清单见 README）

```
agent-assets-sync\
├── README.md            给使用者看的（怎么装、命令一览、怎么改配置）
├── package.json         aas 命令注册（bin）+ 依赖 + localg 本地全局安装
├── sync.config.json     配置：编辑器适配器 / 源登记 / 链接形态映射 / 技能目录 skills（schemaVersion 1）
├── src\
│   ├── main.mjs         CLI 入口（commander 薄壳）
│   ├── sync.mjs         链接形态同步器本体（体检 / 建链接，原先的 sync.mjs）
│   ├── config.mjs       配置规范化（新旧格式都认，含 skills 目录校验）
│   ├── ledger.mjs       安装账本（~/.aas/installed.json：原子写/备份/校验/体检拦截）
│   ├── editors.mjs      编辑器适配器（检测 / 挑选 / 原名→运行时名映射）
│   ├── catalog.mjs      源解析统一（短名→源上下文，--islocal / npx 回退）
│   ├── cli-version.mjs  CLI 依赖版本检查/更新（npm，B2 防自更新）
│   ├── deps.mjs         依赖清单读取 + BFS 解析器（防环、失败不中断批次）
│   ├── add.mjs          aas add（clone 缓存 / 列资产 / 安装 / 记账 / 撞名检查 / 装后解析依赖）
│   ├── update.mjs       aas update（刷新 + 三态漂移修复 + 依赖重校验）
│   ├── remove.mjs       aas remove（摘除 + 销账 + isTTY 守卫）
│   └── import.mjs       aas import（手建条目收编进源仓库）
├── test\                测试（系统临时目录里造假源/假运行时，不碰真实的 ~\.trae-cn；计数取 `node --test "test/*.test.mjs"`）
└── docs\
    ├── design.md        本文档：为什么独立成项目
    └── cli-design.md    CLI 化设计（经 multi-lens-review 4 轮收敛）
```
